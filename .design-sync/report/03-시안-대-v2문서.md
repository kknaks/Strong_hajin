## 1. 상태 어휘가 겹치지 않는다 ★

**① 시안**: 고를 수 있는 상태 3종 = 진행 중 / 막힘 / 완료 (`data.js:65-69`).
데이터에는 `not-started`(보낸 업무) 와 `cancelled`(완료 업무) 가 더 있지만 **고를 수는 없다**.

**② v2**: `open`(시작 전) 이 명시적 상태다 — 「수락하면 … **시작 전 open 유지**」(`생명주기_v2.md` 2.4 표 · 3.1),
「`open → in_progress` 변경 시각이 시작 시각」(4.1).

**③ 어긋나는 지점**
- 시안의 `STATUS_OPTIONS` 에 **`open`(시작 전) 이 없다.** 「내 업무」 표에서 사람이 「시작 전」으로 되돌리거나
  「시작 전 → 진행 중」을 고르는 길이 화면에 없다. v2 에서 시작은 **이 전이가 곧 시작 시각**이라 기록의 원천인데,
  시안의 상태 Select 에는 그 전이가 없다.
- 반대로 「시작 전」은 **보낸 업무 배지로는 존재한다**(`data.js:116`). 같은 상태가 한 탭에서는 보이고
  다른 탭에서는 고를 수 없다.
- 시안의 `progress`/`done` 과 v2 의 `in_progress`/`done` 은 **이름만 다르고 뜻은 같아 보인다** — 다만
  시안에 매핑표가 없어 확언할 수 없다.

## 2. 완료가 한 단계다 — v2 는 두 단계다 ★

**① 시안**: 상태 Select 에서 「완료」를 **바로 고른다** (`data.js:68`, `my-work.v2.jsx:129`).
그 뒤 요청자의 승인 단계를 그리는 화면이 없다. 「완료 업무」 탭의 배지도 `done`「완료」 하나다(`data.js:134`).

**② v2**: 「요청받은 업무는 **수행 결과를 보고하고 요청자의 완료 확인을 받는 방향**이다. 결과 제출과 완료 확인은
구분한다.」(`생명주기_v2.md` 5.1) · 「하위 Task 나 체크리스트가 끝나도 업무를 자동 완료하지 않는다. … **요청받은
업무는 담당자의 완료 보고 후 요청자가 승인해야 완료된다.**」(5.4) · 「완료 보고·승인·보완·재보고」(`example.md:3`)

**③ 어긋나는 지점**
- 시안의 상태 축에 **「완료 보고함 / 승인 대기」 상태가 없다.** (현재 코드에는 `completion_submitted` 가 있다 —
  `frontend/src/lib/viewModels.ts:110`.)
- 다만 시안에 **흔적은 있다**: `badge: '완료 확인'` + `actions: 'confirm'` → 「확인」/「보완 요청」 두 단추
  (`work-data.js` 의 `w8`, `my-work.v2.jsx:135-136`). 이것이 v2 의 승인/보완에 대응하는 것으로 보인다.
  **그러나 그 행의 `status` 는 `progress` 다** — 승인 대기가 별도 상태로 서지 않고 배지로만 표시된다.
- v2 5.1 이 「제출·확인 단계의 정확한 상태값」을 **미정**으로 두었으므로, 이것은 *모순*이라기보다
  **시안이 미정 자리를 배지로 메운 것**이다. 어느 쪽으로 확정할지가 남는다 → **OQ-V2-01**

## 3. 거절이 「행 액션」이다 — v2 에서는 Task 가 취소된다 ★

**① 시안**: `actions: 'accept'` 행에 「수락」/「거절」 두 단추(`my-work.v2.jsx:141-142`). 누르면
`resolveRow(id, '수락'|'거절')` 로 **그 자리에 글자만 남는다**(`my-work.v2.jsx:386`, 셀은 `.scax-task-table__resolved`).
거절 뒤 그 행이 어떻게 되는지를 시안은 그리지 않는다.

**② v2**: 「**거절하면 요청의 거절 사실을 기록하고 Task 를 즉시 `cancelled` 로 전환한다.** 상위 업무에는
'취소됨 — 요청 거절'로 남긴다.」(`정의_v2.md` 2.4 · `생명주기_v2.md` 3.1) ·
「거절 후 재요청은 **새 Task 로 만들고** 같은 상위 업무에 연결한다. **기존 Task 를 재사용하지 않으며**
거절·취소 로그를 보존한다.」

**③ 어긋나는 지점**
- 거절 후 행이 「완료 업무」 탭의 `cancelled` 로 가는지, 목록에서 사라지는지, 제자리에 남는지가 **시안에 없다.**
- 시안의 「다시 요청」(`my-work.v2.jsx:184`)은 **보낸 업무 탭**에 있고, 그 대상 행의 `status` 는 `progress`/`not-started` 다
  (`work-data.js` 의 `x1~x4`) — **거절된 행이 아니다.** v2 의 「거절 후 재요청 = 새 Task」와 같은 것인지
  다른 것인지(단순 독촉인지) 시안 문구만으로는 갈리지 않는다 → **OQ-V2-02**
- v2 의 「'취소됨 — 요청 거절'로 상위에 표시」에 대응하는 자리가 시안에 없다 (상위 개념 자체가 없다 — 4절).

## 4. 상위·하위 Task 가 화면에 없다 ★가장 큰 빠짐

**① 시안**: `WORK_TASKS` 24행 전부가 **평평하다** — `parent`·`children`·`depth` 같은 필드가 하나도 없다
(`handoff/shared/js/work-data.js` 전체). 표도 한 겹이고, 유일한 들여쓰기는 「완료 업무」의 **그룹 머리**
(`.scax-task-table__cell--indent`, `my-work.v2.jsx:217`)인데 그 그룹은 「내 업무 / 보낸 업무」 소유 축이지
상하위가 아니다 (`data.js:128-131`).

**② v2**: 상하위가 이 판의 **중심**이다.
- 「각 담당자에게는 **중심 업무와 직속 하위 작업까지 두 단계만 표시한다.**」(`정의_v2.md` 2.2 · `생명주기_v2.md` 4.2)
- 「**미완료 하위 Task 가 있으면 상위 업무를 완료할 수 없다.**」(`정의_v2.md` 2.6 · `생명주기_v2.md` 5.4)
- 「취소된 하위 Task 는 로그를 보존하되 **상위 완료 검사에서 제외한다.**」(같은 곳)
- `작업계획서_v2.md` 2 「화면 | **중심 업무와 직속 하위 작업 두 단계.** 하위 개수 제한이 아님」

**③ 어긋나는 지점**
- 시안에 **두 단계 표시가 없다.** 하위 작업을 펴는 자리, 상위로 올라가는 자리, 하위의 상태를 상위 행에서 읽는 자리 —
  셋 다 없다.
- 「미완료 하위가 있으면 완료 불가」를 **사람에게 알리는 자리가 없다.** 시안의 상태 Select 는 항상 「완료」를
  고를 수 있게 그려져 있다(`my-work.v2.jsx:129`) — 막히는 경우의 화면이 없다.
- 시안의 유일한 진행 신호는 **체크리스트**뿐인데(7절), v2 는 「체크리스트는 완료 기준이고 **하위 Task 는 이를
  충족하기 위해 수행할 일**이다. 체크리스트와 하위 Task 는 구분한다.」(`정의_v2.md` 2.1 · `생명주기_v2.md` 4.4)
  라고 둘을 명시적으로 갈라 놓았다.
- **「WBS 보기」 단추**(`my-work.v2.jsx:72`)가 이 자리를 맡는 것일 수 있다. 그러나 그 화면은 시안에 없다 → **OQ-V2-03**

## 5. 「보낸 업무」 한 갈래가 v2 의 세 행위를 덮는다

**① 시안**: 탭은 `my`/`sent`/`done` 셋(`data.js:52-56`). `sent` 4행은 전부 「내가 남에게 보낸 것」이고
열은 담당자·기한·상태·「다시 요청」뿐이다(`my-work.v2.jsx:154-191`).

**② v2**: 업무를 만드는 행위가 **셋으로 구분된다** — 「본인 업무 생성 / 업무 요청 / 업무 분배(배정)」
(`정의_v2.md` 1). 「업무 요청과 업무 분배는 모두 상대방을 지정하지만, **서로 다른 기능이다.**
담당자 유무로 구분하지 않는다.」(1.4) 그리고 「각 행위의 생성 시점, 수락·거절, 완료 확인 규칙은 **구분해서 정리한다.**」

**③ 어긋나는 지점**
- 시안의 「보낸 업무」는 **요청과 배정을 가르지 않는다.** 행에 그 구분을 담는 필드가 없다
  (`work-data.js` 의 `x1~x4` 는 `group:'sent'` + `owner` + `status` 뿐).
- v2 는 요청에 **수락 대기 / 협의 중** 상태가 있다(`생명주기_v2.md` 3.1 흐름도: 수락·협의·거절).
  시안의 `SENT_STATUS_LABEL` 은 **`progress`/`not-started` 둘뿐**(`data.js:116`)이라 「수락 대기」·「협의 중」이
  설 자리가 없다. `SENT_TASK_FILTERS` 도 전체/시작 안함/기한 지남 셋뿐이다(`data.js:105-109`).
- 반대로 **「받은 요청」은 시안에서 「내 업무」 탭 안의 칩**이다(`data.js:60`) — 별도 갈래가 아니다.
  v2 는 받은 요청을 「상대방의 수락·협의를 거침」이라는 별도 단계로 본다.
- 「참조」 관계가 시안 업무 표에 없다 (수신함 카드의 badge「참고」로만 존재, `data.js:36-48`).

## 6. 담당자 변경 흐름이 시안에 없다

**① 시안**: `work-data.js` 에 `owner` 는 있으나 **변경 제안·수락 대기·교체를 그린 자리가 없다.**
업무 만들기 모달에도 담당자 필드가 없다 — 있는 것은 「확인받을 사람(선택)」뿐(`work-modal.jsx:230-232`).

**② v2**: 담당자 변경이 **한 절을 차지한다** — 「**새 담당자가 수락할 때 담당을 교체한다.** 수락 대기 중에는
기존 담당과 수행 책임을 유지한다. 새 담당자가 거절하면 기존 담당이 계속 맡으며, 그 거절만으로 업무를
취소하지 않는다.」(`생명주기_v2.md` 3.3 · `정의_v2.md` 2.7)
`작업계획서_v2.md` 4.4 는 이것을 「단계 3 — 담당 변경의 책임 공백 제거」로 따로 잡았다.

**③ 어긋나는 지점**
- 「기존 담당 active + 새 담당 pending 이 동시에 존재」하는 상태를 표의 어느 칸에 낼지 시안에 없다.
- 시안 표의 담당자 열은 **보낸 업무 탭에만** 있다(`my-work.v2.jsx:160`). 「내 업무」 탭에는 요청자 열만 있다.

## 7. 체크리스트 — 만들 때만 있고 수행 중에 없다

**① 시안**: `Checklist` 는 **업무 만들기 모달 안에만** 있다(`work-modal.jsx:120-145`, `:233-241`).
목록 표에 체크리스트 진행률을 내는 칸이 없고, 상세 화면 자체가 시안에 없다.

**② v2**: 「체크리스트는 업무의 **완료 기준**이고, 하위 Task 는 그 기준을 충족하기 위해 수행할 일이다.」
(`정의_v2.md` 2.1) · 「**모든 체크를 완료의 필수 조건으로 강제할지, 체크 권한** — 미정」(`생명주기_v2.md` 4.4)

**③ 어긋나는 지점**
- 완료 기준을 **수행 중에 보고 체크하는 자리가 시안에 없다.** (현재 코드에는 있다 — `ChecklistCue`,
  `frontend/src/features/work/WorkViews.tsx:130`.)
- v2 가 미정으로 둔 「체크 권한」·「필수 조건 여부」를 시안이 답하지 않는다 — 어긋남이 아니라 **양쪽 다 빈칸**.

## 8. 기한 초과 — 표시 방식은 맞고, 필터 축이 새 것이다

**① 시안**: 기한 칸에 빨간 「+N」(`my-work.v2.jsx:124-126`, `.scax-task-table__due-extra`), 칩에 「기한 지남」(`data.js:62`).
상태값은 건드리지 않는다.

**② v2**: 「기한 초과 | **지연 표시만 하고 기존 상태 유지.** 자동 취소·완료하지 않음」(`정의_v2.md` 2.8 · `생명주기_v2.md` 6.1)

**③ 어긋나는 지점**: **없다 — 일치한다.** 다만 「기한 지남」이 상태가 아닌 **파생 필터**로 칩 줄에 상태 칩들과
나란히 서 있어(`data.js:58-63`), 축이 섞여 보인다는 점만 적어 둔다.

## 9. 철회·취소·재개가 시안에 없다

**① 시안**: `cancelled` 는 **완료 업무 탭의 읽기 전용 배지 하나**로만 존재한다(`data.js:134`, `work-data.js` 의 `d4`).
철회·취소 제안·동의·재개를 여는 커맨드가 시안 어디에도 없다.

**② v2**: 여섯 가지 기본값이 표로 정해져 있다(`생명주기_v2.md` 6.1 · `정의_v2.md` 2.8) —
수락 전 철회 / 수락 후 취소 제안+담당자 동의 / 무응답 / 기한 초과 / 본인 업무 재개 / 요청 업무 재개.
「완료된 상위 아래의 하위 재개 | **상위를 먼저 재개해야 하위를 재개할 수 있음**」

**③ 어긋나는 지점**: 이 여섯 중 **화면에 대응이 있는 것은 「기한 초과」 하나뿐**이다(8절). 나머지 다섯은
시안에 자리가 없다. 취소 상태로 가는 길이 화면에 없는데 취소 배지는 있다.

## 10. 유입 경로 — 시안은 메일·메신저를 그리고, v2 는 행위와 분리한다

**① 시안**: 수신함 카드가 출처를 그린다 — 「메일」(`sourceIcon:'mail'`) · 「메신저」(`sourceIcon:'message'`),
외부 링크 아이콘과 함께(`data.js:19-20` · `data.js:45-46`, `my-work.v2.jsx:49-54`).
업무 만들기 모달도 메일 출처 행으로 연다(`MODAL_SOURCE`, `data.js:163`).
카드 단추는 「내 업무로」 / 「답장」(`data.js:21-22`).

**② v2**: 「메일·메신저·회의·AI 채팅·스케줄은 **업무 내용이나 생성 명령이 들어오는 경로다.**
본인 업무 생성·요청·배정 중 **어떤 행위인지와 별도로 구분한다.**」(`생명주기_v2.md` 7) ·
「**메일·스케줄 등의 자동 수락 여부는 추후 각 트리거 설정에서 정한다.**」 ·
**미정**: 「자동 생성의 행위 구분 … **모든 자동 생성을 시스템의 업무 요청으로 간주하지 않는다.**」

**③ 어긋나는 지점**
- 시안의 「내 업무로」 단추가 **세 행위 중 어느 것인지**(본인 업무 생성인가, 시스템이 보낸 요청의 수락인가)가
  화면에 없다. v2 는 바로 그것을 구분하라고 적었다.
- 시안의 수신함 카드에 **badge「업무」/「참고」 두 종류**만 있다(`data.js:3-7`). v2 의 세 행위 구분과 축이 다르다.
- 업무 만들기 모달이 메일 출처를 달고 열리는 것(`data.js:158`)은 v2 7절의 「유입 경로」와 맞는다 — 어긋나지 않는다.

## 11. 「확인받을 사람」 — v2 의 어느 개념인지 불명

**① 시안**: 업무 만들기 모달에 「확인받을 사람 (선택)」 AutoComplete 하나(`work-modal.jsx:230-232`).
추천 목록에 「법무담당」·「계약 검토 이력」·「팀장」 같은 이유가 붙는다(`data.js:172-176`).

**② v2**: 대응하는 말이 **셋 있는데 서로 다르다** —
「요청자의 완료 확인」(`정의_v2.md` 2.3 · `생명주기_v2.md` 5.1), 「참조자」(현재 코드 개념), 「배정자」.
v2 5.2 는 「배정 업무의 완료 확인 필요 여부와 **확인자** — 미정」이라고 그 자리를 비워 뒀다.

**③ 어긋나는 지점**: 시안의 「확인받을 사람」이 v2 의 **완료 확인자**를 가리키는지, 단순 참조자인지가
어느 쪽 문서에도 없다. 본인 업무 생성 모달에 완료 확인자를 넣는다면 그것은 v2 5.2 의 미정을
「본인 업무에도 확인자를 둔다」로 답하는 셈이 된다 → **OQ-V2-04**

## 12. 「WBS 보기」 — v2 에 이 말이 없다

**① 시안**: 칩 바 오른쪽 끝에 「WBS 보기」 단추(`my-work.v2.jsx:72`). 여는 화면은 시안에 없다.

**③ 어긋나는 지점**: 4절의 「두 단계 표시」와 같은 것을 가리키는 다른 이름일 수 있으나, 확인할 근거가 없다.
